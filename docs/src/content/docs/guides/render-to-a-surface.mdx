A surface session draws the map into a native surface your window toolkit owns,
and presents through it. You own the window and the graphics context; MapLibre
draws into them.

## What you hand over

You do not give MapLibre a window. You give it the low-level surface handle your
toolkit already produced, which depends on the render backend your artifact was
built with:

| Backend      | You supply      | Presented with       |
| ------------ | --------------- | -------------------- |
| Metal        | `CAMetalLayer*` | The layer's drawable |
| Vulkan       | `VkSurfaceKHR`  | A swapchain          |
| OpenGL (EGL) | `EGLSurface`    | `eglSwapBuffers`     |
| OpenGL (WGL) | `HDC`           | `SwapBuffers`        |

Getting that handle is the platform's job, not MapLibre's: wrap an
`ANativeWindow*` in an `EGLSurface` or `VkSurfaceKHR` on Android, create one
from your X11 or Wayland window on Linux, take the window's `HDC` on Windows,
hand over the view's `CAMetalLayer` on Apple platforms.

Along with the surface you supply a **context** — the backend objects the
session shares with your application, so the map's textures and buffers live in
the same world as yours. A Metal device; a Vulkan instance, device, and graphics
queue; an EGL or WGL share context. The session joins that share group rather
than taking it over.

Finally the descriptor carries an **extent**: the logical size in UI pixels plus
the scale factor. Attaching replaces whatever size the map was created with.

## Drive the frame loop

Rendering is pull-based. MapLibre never draws on its own; it tells you it has
something to draw and waits for you to ask for it. Each turn of your loop:

1. Pump the runtime and drain its events.
2. `MAP_RENDER_UPDATE_AVAILABLE` for your map means new content is ready — mark
   a frame as pending.
3. If a frame is pending, call `mln_render_session_render_update()`. For a
   surface session this renders *and* presents.

Two details make the difference between a map that settles and one that stalls.
A render call reports whether it actually produced a frame; `false` early on is
normal, because the map has not published its first update yet — stay pending
and try again. And finished-frame events carry a `needs_repaint` flag, which is
how camera animations and label placement ask for the next frame. Ignore it and
animations freeze partway.

What paces the loop is up to you. Prefer the display where you can — a vsync or
frame callback from your toolkit. The example apps poll with a short sleep,
which is simple and burns CPU.

## Resize

When the window changes size, call `mln_render_session_resize()` with the new
logical size and scale factor, then render again. The camera, style, and sources
live on the map and survive; renderer-held state such as feature state does not,
so reapply it afterward.

A scale factor that disagrees with the map's own logs a warning and renders
imagery chosen for the map's density. Pick the map's `scale_factor` for the
displays you actually target.

## Follow the surface's life

Surfaces come and go as windows close and views detach. When the surface goes
away:

1. Destroy the session with `mln_render_session_destroy()`, or release the map's
   slot with `mln_render_session_detach()` and destroy the handle after. A
   detached handle is finished: it cannot render, and it cannot be reattached.
2. Release your surface and context.
3. When a new surface arrives, attach a fresh session. The map kept its camera
   and style the whole time.

Complete working loops for each backend live in the example apps: `zig-map`,
`rust-map`, `lwjgl-map`, `swift-map`, `dotnet-map`, and `android-map`.
