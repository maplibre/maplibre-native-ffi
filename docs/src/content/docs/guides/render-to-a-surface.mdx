A surface session draws the map into a native surface your window toolkit owns
and presents through it. You own the window and the graphics context, and
MapLibre draws into them.

## What you hand over

Attach the low-level surface handle your toolkit already produced. Which handle
depends on the render backend your artifact was built with.

| Backend      | You supply      | Presented with       |
| ------------ | --------------- | -------------------- |
| Metal        | `CAMetalLayer*` | The layer's drawable |
| Vulkan       | `VkSurfaceKHR`  | A swapchain          |
| OpenGL (EGL) | `EGLSurface`    | `eglSwapBuffers`     |
| OpenGL (WGL) | `HDC`           | `SwapBuffers`        |

Each platform produces that handle its own way. On Android you wrap an
`ANativeWindow*` in an `EGLSurface` or a `VkSurfaceKHR`. On Linux you create one
from your X11 or Wayland window, on Windows you take the window's `HDC`, and on
Apple platforms you hand over the view's `CAMetalLayer`.

The descriptor also carries a context: the backend objects the session shares
with your code, so the map's textures and buffers live alongside yours. That
means a Metal device, or a Vulkan instance with its device and graphics queue,
or an EGL or WGL share context. The session joins that share group.

Last, the descriptor carries an extent: the logical size in UI pixels plus the
scale factor. Attaching overwrites whatever size you created the map with.

## Drive the frame loop

Rendering is pull-based. MapLibre tells you it has something to draw and waits
for you to ask for it. Each turn of your loop:

1. Pump the runtime and drain its events.
2. On `MAP_RENDER_UPDATE_AVAILABLE` for your map, mark a frame as pending.
3. While a frame is pending, call `mln_render_session_render_update()`. A
   surface session renders and presents in that one call.

Steps 1 and 2 run on the runtime's owner thread and step 3 on the session's. One
thread can do all three.

Two details keep a map moving. The render call reports whether it produced a
frame, and a `false` result is normal whenever the map has yet to publish an
update for the session's extent, which covers startup and the turns just after
an attach or resize; stay pending and call again. Finished-frame events carry a
`needs_repaint` flag, which is how camera animations and label placement ask for
the next frame. Drop that flag and animations freeze partway.

What paces the loop is your choice. Prefer the display where you can, through a
vsync or frame callback from your toolkit. The example apps poll with a short
sleep, which is simple and burns CPU.

## Resize

When the window changes size, call `mln_render_session_resize()` with the new
logical size and scale factor, then render again. Camera, style, and sources
live on the map, and the session keeps its renderer, so tiles, atlases, and
renderer-held state such as feature state carry over. Changing the scale factor
is the exception: a renderer compiles its shaders for one pixel ratio, so that
resize starts a new one and renderer-held state starts empty.

A scale factor that disagrees with the map's own logs a warning, and MapLibre
renders imagery chosen for the map's density. Choose the map's `scale_factor`
for the displays you target.

## Follow the surface's life

Surfaces come and go as windows close, views detach, and devices rotate. When a
new surface arrives on the same graphics context, hand it to the live session
with `mln_<backend>_surface_set_target()`. The session keeps its renderer, so
the map comes back with the tiles and atlases it already had instead of
rebuilding them. This is the path for Android rotation, a Flutter
`SurfaceProducer` lifecycle change, and any window resize that reallocates.

Tear the session down when the graphics context itself goes away, or when the
replacement belongs to a different one:

1. Call `mln_render_session_destroy()` on the thread that attached the session.
   To release the map's slot first, call `mln_render_session_detach()` and
   destroy the handle afterward. A detached handle can only be destroyed.
2. Release your surface and context.
3. When a new surface arrives, attach a fresh session. The map keeps its camera
   and style throughout, and the new session starts with a cold renderer.

Complete working loops for each backend live in the example apps: `zig-map`,
`rust-map`, `lwjgl-map`, `swift-map`, `dotnet-map`, and `android-map`.
