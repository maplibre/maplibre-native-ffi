A render session draws one map into one render target. A map has at most one
live render session. Its style, sources, layers, and camera remain after the
session detaches.

## Choose a target and driver

A native surface draws and presents each frame to a window or view. A
session-owned texture draws into a ring that the session allocates. A borrowed
texture draws into a ring of textures that the host allocates. [Render a static
image](/maplibre-native-ffi/guides/render-a-static-image/) covers texture
readback.

Execution placement is a separate choice. A core-worker driver owns a native
serial graphics worker and requires transferable graphics state. A
caller-graphics-thread driver stores work until the host services it where the
graphics context is usable. The
[render session concepts](/maplibre-native-ffi/concepts/#render-session) table
gives the driver that each target kind accepts.

The common attach options select the driver and request an owned-texture ring
depth from one to three. They also carry direct wake callbacks for frame-result
readiness and caller-driver work. A host may omit either wake and poll instead.

Each backend attach function copies its descriptor and options, returns a render
session in the attaching state, and accepts a one-shot completion. A caller
driver must service ready driver work before attachment can complete. Await the
completion before using the attached session for ordinary work.

### Share a Vulkan queue

A Vulkan session submits to the graphics queue in its context descriptor, from
its driver's thread. Vulkan requires the host to synchronize every call on a
queue, so a host that also submits to that queue passes a queue lock in the
attach options. The session takes the lock around each of its calls on the
queue, and the host takes the same lock around its own. The host releases the
lock before it calls the C API, because the driver may need the lock to finish
that call. With the lock, one queue serves both the host and a core-worker
session, even on a device whose graphics family has a single queue.

## Replace, detach, or abandon

Resize and target replacement are ordered asynchronous calls. They may start
from any thread. A caller driver applies them when the host next services ready
work on the graphics thread. Resize assigns a new extent generation; later frame
demands capture that generation.

<Code code={region(renderTarget, "resize")} lang="c" title="render-target.c" />

A borrowed texture gets its size from the host allocation, so resizing it
reports an unsupported status. Release every acquired frame, allocate a ring of
as many textures at the new size, and replace the target with a new descriptor.
A frame rendered before the replacement can no longer be acquired, and the host
keeps the outgoing textures until the replacement completes. A host can replace a native surface the same
way after recreating a window or view allocation; Android rotation and Flutter
surface lifecycle changes use this path. Both paths preserve the session's
rendering resources, including loaded tiles, and leave map-owned feature state
unchanged.

<Code code={region(renderTarget, "set-target")} lang="c" title="render-target.c" />

A session's scale factor is fixed at attachment because its shaders use a fixed
pixel ratio, so a resize that names a different one reports an invalid-argument
status. Detach the session and attach a new one at the new scale factor.
Map-owned feature state survives that, and the next render update pushes it into
the new session.

Normal detach completes asynchronously. The selected driver destroys graphics
resources on its graphics thread and detaches the map. Continue servicing a
caller driver until the completion runs, then destroy the detached session
handle from any thread. A session-owned texture ring is the exception when a
frame was disposed instead of released with consumer synchronization: the host's
GPU may still read that frame's texture, so detach keeps the ring allocated
until the process exits. Once detach completes, the host may destroy its
graphics objects, except the Vulkan device behind a kept ring, which stays until
the process exits.

Abandon is the failure path for a host that can no longer service graphics
work. It closes control and mailboxes, invalidates graphics accessors, and
detaches the map without a driver call. On a core-worker session it first waits
for the worker's current driver call to end, since that call can outlive the
frame result or completion it published. It returns busy while a borrowed view
scope is active, while a caller driver's service call is in flight, or when
called from inside one of the session's own driver calls.

Abandon then destroys the session's Vulkan and Metal objects on the calling
thread, after a Vulkan session waits for the work it submitted to its queue.
OpenGL and WebGPU objects belong to their graphics thread, so abandon keeps them
until the process exits. It also keeps a session-owned texture ring while the
host holds a frame of it, or after the host disposed of a frame without
consumer synchronization. The result reports the count of kept resources. To
let abandon destroy a session-owned ring, release acquired frames with consumer
synchronization first. Releasing an acquired frame after abandon remains
CPU-only and consumes the frame handle. Once abandon returns, the host may
destroy its graphics objects, except the Vulkan device and surface behind a kept
Vulkan object, which stay until the process exits. Destroy the abandoned session
afterward.
