An offline region downloads everything a style needs for an area ahead of time,
so the map keeps working with no network. Regions live in the runtime's cache
database, which means `cache_path` has to be a real filesystem path — with
`":memory:"` they last exactly as long as the process.

## Every offline call is asynchronous, the same way

This is the one pattern to learn; every operation follows it.

1. Call a `..._start` function. It validates and returns an **operation ID**.
2. Keep pumping the runtime. Completion arrives as an
   `OFFLINE_OPERATION_COMPLETED` event carrying that ID, what kind of operation
   it was, and its own result status — separate from the status that starting it
   returned.
3. Take the result with the matching `..._take_result` function, if the
   operation produces one.

Operations that produce no result — delete, invalidate, set download state, set
observed, ambient cache maintenance — finish at step 2. Either way the operation
holds runtime state until it is consumed or discarded, so discard the ones you
do not take. A failed take deliberately leaves the operation alive so you can
retry it; discard it when you give up.

## Create a region

Two kinds of definition:

* **Tile pyramid** — everything inside a bounding box, between a min and max
  zoom, at a given pixel ratio. An infinite max zoom means "each source's own
  maximum".
* **Geometry** — the tiles covering an arbitrary geometry, such as a route
  corridor, across a zoom range.

Creation also takes **metadata**: opaque bytes stored with the region and handed
back on every later inspection. A name, or a JSON blob, usually.

A new region is inactive and silent. Mark it observed to get progress events,
then set its download state to active to start the work.

## Watch it download

Three events report on a region being observed:

| Event                                      | Tells you                                                       |
| ------------------------------------------ | --------------------------------------------------------------- |
| `OFFLINE_REGION_STATUS_CHANGED`            | A status snapshot: resource and tile counts, sizes, done or not |
| `OFFLINE_REGION_RESPONSE_ERROR`            | One resource failed, and why                                    |
| `OFFLINE_REGION_TILE_COUNT_LIMIT_EXCEEDED` | The region wants more tiles than the ceiling allows             |

<Aside type="caution">
  Deriving a percentage from the status snapshot needs care: while MapLibre is
  still discovering what the region contains, the required-resource count is an
  estimate, and it is zero before discovery finds anything. Check that the count
  is marked precise and non-zero before dividing by it, or your progress bar will
  show `NaN` on the first event.
</Aside>

Exceeding the tile ceiling is not something you can raise through this API — the
event reports the limit, and the fix is a smaller region: tighter bounds or a
narrower zoom range.

## Manage what you have downloaded

* `list` — every region in the database, with definitions and metadata.
* `get` — one region; the completion event's `found` flag says whether it exists.
* `update_metadata` — replace the stored bytes.
* `merge_database` — import regions from a side database, such as one you
  shipped with the app.
* `invalidate` — mark a region's resources stale so their next use revalidates
  against the server. This frees no space: the bytes stay and get reused when
  revalidation succeeds.
* `delete` — remove the region and its resources.

Cache maintenance runs through `ambient_cache_operation_start`. `INVALIDATE` and
`CLEAR` act on ambient cached resources and leave offline regions alone, and
`PACK_DATABASE` compacts the file.

<Aside type="danger">
  `RESET_DATABASE` is different in kind: it deletes and recreates the whole
  shared database, so downloaded regions go with it. It is not a bigger cache
  clear.
</Aside>
