The camera lives on the map and moves independently of rendering. All camera
calls run on the map owner thread and take effect as the runtime pumps.

## Camera state

Camera state is a single options struct — center, altitude, zoom, bearing,
pitch, roll, field of view, padding, and anchor — where each field is
individually optional. When you **set** the camera, only the fields you mark
apply; the rest stay unchanged. When you **get** the camera, you receive a
snapshot with the current values filled in.

Two details to know:

* `anchor` is the screen-space focal point for a camera command. It is
  input-only: snapshots never include it.
* Positions and sizes are in **logical (UI) pixels**, origin top-left — never
  device pixels.

## Transitions: jump, ease, fly

Three commands apply camera options:

* `jump_to` — instant.
* `ease_to` — eased transition. The default duration is **zero**: without an
  explicit duration it behaves like a jump. Set `duration_ms` to animate.
* `fly_to` — flight transition, and the one command that **animates by
  default**. Without a duration, the native code derives it from distance and
  `velocity` (default 1.2 screenfuls per second); `min_zoom` controls how far
  the flight zooms out at its peak.

Animation options also accept a cubic `easing` curve. Cancel any in-flight
transition with `cancel_transitions()`.

## Relative gestures

Pan, zoom, rotate, and pitch come in relative ("by") form only, each with an
animated variant (same zero-duration default as `ease_to`):

* `move_by(delta_x, delta_y)` — screen-space pan, in logical pixels.
* `scale_by(scale, anchor)` — zoom by a factor around an optional anchor.
* `rotate_by(first, second)` — rotate between two screen points.
* `pitch_by(pitch)` — pitch delta in degrees.

Absolute targets go through `jump_to` / `ease_to` / `fly_to` with the fields
you want to change.

```kotlin
// Kotlin; the other bindings mirror these one-to-one.
map.moveBy(deltaX, deltaY)
map.scaleBy(1.5, ScreenPoint(x, y))
map.rotateBy(firstTouch, secondTouch)
map.pitchBy(10.0)
```

## Fit the camera to content

The `camera_for_*` family computes a camera that fits content in the current
viewport, without applying it. Apply the result yourself with `jump_to` or
`ease_to`:

* `camera_for_lat_lng_bounds(bounds, fit_options)` — fit a bounding box.
* `camera_for_lat_lngs(coordinates, fit_options)` — fit a coordinate list.
* `camera_for_geometry(geometry, fit_options)` — fit a geometry.

Fit options add `padding` (edge insets in logical pixels), `bearing`, and
`pitch` to the computed camera. The inverse —
`lat_lng_bounds_for_camera(camera)` — reports the geographic bounds a camera
covers.

## Constrain the camera

`mln_map_set_bounds()` applies camera constraints: geographic `bounds`,
`min_zoom` / `max_zoom`, and `min_pitch` / `max_pitch`. Only the fields you
mark apply, and paired min/max fields must be consistent. Read the active
constraints with `mln_map_get_bounds()`.

## Convert between screen and geographic coordinates

On the live map:

* `pixel_for_lat_lng` / `lat_lng_for_pixel` — single conversions, plus batch
  variants. Pixels are logical, origin top-left.
* `mln_map_projection_create(map)` — snapshot the map's transform into a
  standalone **projection helper**. It survives later camera moves and even
  map teardown, and answers the same conversions against the frozen camera —
  useful for placing UI overlays between frames.
* `projected_meters_for_lat_lng` / `lat_lng_for_projected_meters` — stateless
  spherical Mercator conversions, no map needed. Higher-level metrics such as
  meters-per-pixel are host arithmetic on top of these.

## Observe camera movement

Camera transitions emit `MAP_CAMERA_WILL_CHANGE`, `MAP_CAMERA_IS_CHANGING`,
and `MAP_CAMERA_DID_CHANGE` events. Poll `mln_map_get_camera()` during
`IS_CHANGING` to mirror the animated position into host UI.
