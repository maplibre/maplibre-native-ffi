An integration needs the native library, which implements the C API. Unless you
call C directly, it also needs a language binding that wraps it. CI compiles the
native library per platform and per render backend, so pick the artifact
matching your target.

## Get the native library

CI publishes CPack archives to the floating
[`unstable-native-snapshot`](https://github.com/maplibre/maplibre-native-ffi/releases/tag/unstable-native-snapshot)
prerelease, named `maplibre-native-c-<preset>.tar.gz` alongside a `SHA256SUMS`
manifest. Presets are `<os>-<arch>-<backend>`:

| Platform | Presets                                                                              |
| -------- | ------------------------------------------------------------------------------------ |
| Linux    | `linux-x64-egl`, `linux-x64-vulkan`, `linux-arm64-egl`, `linux-arm64-vulkan`         |
| macOS    | `macos-arm64-metal`, `macos-arm64-vulkan`, `macos-arm64-egl`                         |
| Windows  | `windows-x64-wgl`, `windows-x64-vulkan`, `windows-arm64-wgl`, `windows-arm64-vulkan` |
| Android  | `android-arm64-egl`, `android-arm64-vulkan`, `android-x64-egl`, `android-x64-vulkan` |
| iOS      | `ios-arm64-metal`, `ios-simulator-arm64-metal`                                       |

`egl` and `wgl` both mean the OpenGL backend, and the suffix names the context
provider. The OpenHarmony presets `ohos-arm64-egl` and `ohos-arm64-vulkan` build
from source, and CI publishes no archive for them.

An unpacked archive holds the umbrella header `maplibre_native_c.h` and its
domain headers under `include/`, the library under `lib/` (`bin/` on Windows), a
pkg-config descriptor under `share/pkgconfig/`, and
`share/maplibre-native-c/artifact.json`, which records the backend and platform
the artifact was built for.

### Or build it yourself

The repository builds with CMake presets driven by [mise](https://mise.jdx.dev):

```bash
mise bootstrap --yes            # system packages, tools, hooks
mise run build                  # host library for this machine
mise run build linux-x64-vulkan # a specific preset
```

The install tree lands in `build/<preset>/install` with the archive's layout.

## Package an Android app

Every Android app needs two things from this project, whatever language it is
written in: the C library, and the TLS component that reaches the platform trust
policy. The runtime AARs carry both, so one Gradle coordinate covers the
packaging.

```kotlin
repositories {
  maven {
    url = uri("https://central.sonatype.com/repository/maven-snapshots/")
    content { includeGroup("org.maplibre.nativeffi") }
  }
  mavenCentral()
}

dependencies {
  implementation("org.maplibre.nativeffi:maplibre-native-ffi-runtime-vulkan:$version")
}
```

A runtime AAR holds `libmaplibre-native-c.so` for each ABI, the patched
[`rustls-platform-verifier`](https://github.com/rustls/rustls-platform-verifier)
helper that the native TLS stack calls over JNI, and the R8 keep rule that helper
depends on. The library links libc++ statically, so this is the whole native
payload. Pick the runtime matching your backend; an app packages one of them.

Kotlin apps add `org.maplibre.nativeffi:maplibre-native-ffi` for the API on top.
Hosts in other languages depend on the runtime alone and reach the library
through their own FFI. Native code is the only caller of the TLS helper, so
these hosts bind nothing in it: the class needs to be in the APK, and the keep
rule arrives with it.

Call `mln_android_init` once from any language with a `JNIEnv*` and an
`android.content.Context` before creating a runtime. Android HTTP requests
validate TLS against the app's platform trust policy from that point on.

The CPack `android-*` archives hold the same library with the public headers,
for a host that assembles its own AAR or builds the library into one. They carry
no Java classes, so such a host also packages the helper AAR built by
`mise run //bindings/rustls-platform-verifier-android:build`.

## Point a C project at it

The public headers target C23, and the archive ships pkg-config in place of a
CMake package config:

```bash
export PKG_CONFIG_PATH=/opt/maplibre-native-c/share/pkgconfig
cc -std=c23 main.c $(pkg-config --cflags --libs maplibre-native-c) -o main
```

Static archives define `-DMLN_STATIC` through the same descriptor, so one
command covers both linkage modes. On Windows the runtime DLL lands in the
prefix's `bin/`, which stays off the search path, so add that directory to
`PATH` or copy the DLL next to your executable.

To confirm the install, ask the library what it is:

```c
printf("ABI version: %u\n", mln_c_version());
printf("backends: %#x\n", mln_supported_render_backend_mask());
```

## Language bindings

Bindings live under `bindings/` for Kotlin, Rust, Swift, Zig, .NET, Python, Go,
and Dart. Only the Kotlin artifacts are published anywhere today, as
`org.maplibre.nativeffi` snapshots on
[Maven Central's snapshot repository](https://central.sonatype.com/repository/maven-snapshots/org/maplibre/nativeffi/).
For the rest, depend on the binding by path or git from a checkout and point its
build at a native install prefix.

### Rust

The Rust binding fetches the native library itself, so a git dependency needs no
separate install:

```toml
[dependencies]
maplibre-native = { git = "https://github.com/maplibre/maplibre-native-ffi" }
```

The build script downloads the archive matching your target from the snapshot
release, verifying it against the release's `SHA256SUMS` and caching it under
your user cache directory. Pick a render backend with a feature — `vulkan`,
`opengl`, or `metal`, at most one — or take the platform default (`vulkan` on
Linux and Windows, `metal` on macOS). Device iOS is the one published preset
this cannot serve, because `ios-arm64-metal` ships only a static archive; take
the tarball by hand for that target.

Setting `MAPLIBRE_NATIVE_C_INSTALL_DIR` to a local install prefix skips the
download entirely, which is what `mise run //bindings/rust:test` does.

The download covers building, not running. The library is dynamic, and Cargo
applies a dependency's link arguments to that dependency alone, so your own
binaries and tests need the loader pointed at the prefix. The crate publishes it
as `DEP_MAPLIBRE_NATIVE_C_RUNTIME_DIR`. On Linux and macOS a build script of your
own turns that into an rpath:

```rust
// build.rs
fn main() {
    let dir = std::env::var("DEP_MAPLIBRE_NATIVE_C_RUNTIME_DIR").unwrap();
    println!("cargo:rustc-link-arg=-Wl,-rpath,{dir}");
}
```

That needs a direct `maplibre-native-sys` dependency, since Cargo passes `DEP_*`
to immediate dependents only. Setting `LD_LIBRARY_PATH` or `DYLD_LIBRARY_PATH`
to that directory works too, and is what the repository's own test tasks do.
Windows has no rpath: there the variable names the `bin/` holding
`maplibre-native-c.dll`, and the executable needs that directory on `PATH` or a
copy of the DLL beside it.

An Android target resolves to the `android-*` archive, which carries the library
alone. Such an app still packages the TLS helper and calls `mln_android_init`,
as [Package an Android app](#package-an-android-app) describes; the sys crate
exposes that entry point along with the rest of the C API.

Because the snapshot release republishes on its own schedule, its C headers can
lag the commit you pinned. The generated declarations follow the artifact rather
than the checkout, so a lagging snapshot shows up as missing `mln_*` items while
compiling `maplibre-native-core`. The build script names the differing headers
when that happens, though Cargo prints build script warnings for git
dependencies only under `cargo build -vv`. Build the native library from source
and set `MAPLIBRE_NATIVE_C_INSTALL_DIR` when you need a specific commit.
