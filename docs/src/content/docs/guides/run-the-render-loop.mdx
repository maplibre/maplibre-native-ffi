MapLibre Native makes progress only while the host pumps the runtime. A pump
runs the work that the map has queued, such as style parsing, tile loads, and
camera transitions, and it services the runtime's own network and database work.
Drawing is a separate call: the map publishes a render update, and the render
session draws it.

Pumping the runtime and polling it for events both run on the runtime owner
thread, and either one reports a wrong-thread status from anywhere else. The
first decision is therefore which thread pumps.

## Choose which thread pumps

Pump from the display thread when your host already has a frame callback and the
map is the main work on that thread. The runtime, the map, and the render
session then share one thread, and the loop needs no shared state at all. The
cost is that a pump drains to completion, so one call can span a whole style
parse. Budget a pump as variable work rather than as a fixed slice of a frame.

Pump from a thread of your own when a long pump must not stall the display, when
the map must keep loading while the display sits idle, or when the host draws no
frames at all. That thread parks inside the pump, so the runtime's own work sets
how often the loop runs, and the display thread attaches the render session and
draws. The cost is a second thread, a little shared state, and a wake source.

## Pump from the frame callback

Pass a timeout of zero. The call drains what is queued and returns, because the
display already sets the pace.

The helper compares each event's source against the map before reading the rest
of it, because one runtime can own several maps, and every map's events share
one queue. It reports a frame on a render update, and on a finished frame whose
repaint flag is set. That second case is how
camera animations and label placement settle over several frames.

A host that stops requesting frames when the map goes idle has one trap to
close. Pumping happens inside the frame callback, so with no frames there is no
pump, and a style edit or a source update made while idle never advances: the
new layer stays invisible until something unrelated asks for a frame. Ask for
one after any change your host makes to the map.

Draw the pending frame after the drain. Keep the frame pending and call again on
the next turn whenever the render call reports that it drew nothing, which means
that the map has published no update for this session's extent yet. That
result is ordinary at startup and on the turns right after an attach or a
resize.

## Pump on a thread of your own

The pump thread owns the runtime and the map, and the display thread owns the
render session. A pump call from the display thread returns
a wrong-thread status, and a render call from the pump thread does the same.

The two threads share a flag that the pump thread sets when a frame is due, a
flag that the display thread sets to stop the loop, and a wake source.

Any thread may signal the source, and the signal releases a parked pump. The
display thread signals it after it queues work for the map or asks the loop to
stop.

<Code code={region(pumpThread, "signal")} lang="c" title="pump-thread.c" />

The loop parks inside the pump until a wake arrives: the owner thread receiving
work, the runtime queueing an event, or a signal on the wake source. Pass a
positive timeout rather than a negative one, because the runtime registers no
timers of its own, and the bound is what lets the loop reach its own stop check
when no wake arrives. This snippet parks for 100 ms, so the loop notices a stop
request at least ten times a second.

<Code code={region(pumpThread, "loop")} lang="c" title="pump-thread.c" />

Call a parking pump outside any lock that a signalling thread also acquires. The
display thread reads the pending flag on its next frame and draws.

Own that thread outright. The owner thread is a specific operating-system
thread, fixed when the runtime is created, and serialization is a weaker
guarantee than affinity: a serial dispatch queue, an actor, or a pooled executor
each promise that your calls happen one at a time, while none of them promises
they happen on one thread. Work scheduled that way lands wherever the pool has
room, and the wrong-thread failures that follow appear at random.
