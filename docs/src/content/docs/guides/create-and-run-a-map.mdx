If you know MapLibre from the web or from the Android and iOS SDKs, you know
what a map does. What is new here is that nothing runs on its own. There is no
map view driving a render loop and no background thread advancing the state
machine — you create the pieces, you call the function that lets MapLibre do
work, and you decide when frames happen.

This guide builds the skeleton every integration shares. It renders nothing yet;
rendering attaches on top of it.

## Two shapes of integration

Almost everything built on this API is one of two things, and knowing which one
you are building decides most of what follows.

**An application, or an SDK under one.** A window or view exists, the map should
follow the user's gestures, and frames keep coming as tiles arrive and labels
settle. You will attach a
[surface session](/maplibre-native-ffi/guides/render-to-a-surface/) and drive it
from your toolkit's frame loop.

**A snapshotter.** A raster tile server, a CLI that writes a PNG, a batch job
rendering map images. There is no window and often no display at all. You want
one finished image per request, then to move on. You will create the map in
static or tile mode and attach a
[texture session](/maplibre-native-ffi/guides/render-to-a-texture/).

The lifecycle below is the same either way.

## Everything happens on one thread

The runtime, its maps, and their render sessions are **owner-thread affine**:
whichever thread creates the runtime owns all of it, and calls from any other
thread are rejected rather than silently racing. One thread can own one runtime.

This is the constraint that surprises people, so decide early which thread that
is. In a GUI app it is usually the UI thread. In a server it is usually a
dedicated worker per rendering slot — spin up several threads, each with its own
runtime and map, if you want concurrent renders.

Callbacks are the exception: resource transforms and providers run on MapLibre's
own network and worker threads, and they say so where they are documented.

## Create a runtime

The runtime owns the scheduler and the event queue. Its options decide where
bytes live:

* `cache_path` — the ambient cache database, where tiles, glyphs, and sprites
  persist between runs. `":memory:"` keeps it in memory instead.
  [Offline regions](/maplibre-native-ffi/guides/download-offline-regions/) live
  in this database too, so give it a real path if you plan to use them.
* `asset_path` — the filesystem root that `asset://` URLs resolve against.
* `maximum_cache_size` — a cap in bytes, applied only when you also set its flag
  in `flags`.

## Create a map

A map belongs to a runtime, and a runtime can own several. Map options set the
starting viewport:

* `width` and `height` — the logical viewport in UI pixels, the same units the
  camera and hit-testing use. Attaching a render session replaces these with the
  session's extent, so they matter mainly before you attach one.
* `scale_factor` — the UI-to-device pixel ratio, and the one option you cannot
  change later. It picks which sprite, glyph, and raster densities the map
  requests for its whole life, so set it to the density you intend to render at.
* `map_mode` — `CONTINUOUS` for a live map, `STATIC` for one-off stills of an
  arbitrary viewport, `TILE` for one-off stills of a single tile. This is the
  application/snapshotter fork from above.

A map is independent of any render target. You can load a style, move the
camera, add sources and layers, and watch events on a map that has never
rendered anything.

## Load a style

`mln_map_set_style_url()` fetches a style document and everything it references;
`mln_map_set_style_json()` takes one inline. Both are **commands**: an OK status
means the request was accepted, not that the style loaded. The outcome comes
back as an event — `MAP_STYLE_LOADED` or `MAP_LOADING_FAILED`, the latter
carrying a message. A URL that 404s still returns OK synchronously and fails
later, so report style errors from the event stream.

## Let MapLibre do work

MapLibre makes progress only while you pump the runtime, and pumping has two
halves:

`mln_runtime_run_once()` drains the owner thread's work — queued tasks, the
tasks those tasks queue, expired timers, and ready network and database work. It
does not block on an idle runtime, but it is a *drain*, not a time slice: one
call can span a whole style parse. Do not treat it as a fixed per-frame cost.

`mln_runtime_poll_event()` pops one queued event per call until it reports none
left. Events from every map under the runtime share this one queue, so check
`event.source` against the map you care about. Payload and message pointers are
borrowed until the next poll — copy anything you keep.

The events worth knowing on day one:

| Event                                     | Meaning                                                            |
| ----------------------------------------- | ------------------------------------------------------------------ |
| `MAP_STYLE_LOADED` / `MAP_LOADING_FAILED` | How the style request turned out                                   |
| `MAP_RENDER_UPDATE_AVAILABLE`             | The map has new content to draw — this is what drives a frame loop |
| `MAP_RENDER_FRAME_FINISHED`               | A frame completed, and says whether another is needed              |
| `MAP_CAMERA_WILL` / `IS` / `DID_CHANGE`   | Camera transition progress                                         |
| `MAP_STILL_IMAGE_FINISHED` / `FAILED`     | A requested still image resolved, in static and tile modes         |
| `MAP_STYLE_IMAGE_MISSING`                 | The style wants an image ID nobody supplied                        |

How often you pump is your call. A GUI app pumps once per frame; a headless tool
pumps in a loop until it gets the event it is waiting for.

## Tear down in order

Handles form a chain — runtime owns maps, maps own render sessions — and a
parent refuses to close while a child is live. Close them in the reverse of the
order you created them: session, then map, then runtime.

Two things catch people out:

**Destroying a map drops its queued events.** There is no flush and no final
event. If you mirror map state from events, read what you need before you close
the map that produces them.

**Garbage collection will not do this for you.** Finalizers, `Drop`, and
`using` blocks in the bindings report leaks; they do not stand in for closing a
thread-affine handle on its owner thread. Close explicitly.

<Aside>
  Bindings add what their language needs to make the owner-thread rule
  enforceable — Go pins a goroutine with `runtime.LockOSThread()`, .NET offers an
  `OwnerThread` helper that runs closures on a dedicated thread, Zig takes an
  allocator and a diagnostic store. The model underneath is the one above.
</Aside>
