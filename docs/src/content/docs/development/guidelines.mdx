Follow these guidelines when you change a binding's API or the documentation.

If a rule doesn't fit a case, change the rule in the same PR instead of making
an exception. When a tool enforces a rule, delete it here.

## Versioning

The native library and every binding share one version number,
`EPOCH.YYYYMM.REVISION`. `YYYYMM` is the UTC year and month of the release.
`REVISION` numbers the releases in that month, starting at 0.

The epoch says what stays compatible. In epoch 0, nothing does: make breaking
changes when they improve the API, and don't add compatibility shims. In epoch 1
and later, a release doesn't break the API, ABI, or documented behavior of
earlier releases with the same epoch, in the library or in any binding. A
breaking change increments the epoch. `MLN_C_VERSION` and `mln_c_version()`
equal the epoch.

## API

The C API is [mln-rs](https://github.com/louwers/mln-rs)'s: its headers, which
`include/` copies, follow its
[C API guidelines](https://github.com/louwers/mln-rs/blob/main/crates/mln_c/README.md#api-guidelines).
A generator in `tools/bindgen` reads them and writes each language binding's
declarations. It reads the headers' `MLN_BINDING` annotations to write safe
wrappers in each binding.

### Bindings

- Every binding names a handle's teardown functions `release` and `dispose` in
  its own case, such as `ReleaseAsync` and `Dispose` in .NET, and has no other
  name for either. Its scoped cleanup calls one of them: a scope that can wait
  without blocking a thread, such as `await using`, calls the release, and every
  other scope, such as a destructor or Python's `with`, calls the dispose.
- Every binding presents a callback registration struct as a type of its own,
  even one that holds a single callback, so the struct can gain members without
  breaking callers.
- Some language bindings may not expose callbacks without a delivery queue, or
  may expose that functionality with an alternative declarative API.
- Every binding presents a struct that holds a kind and a union of its variants
  as a sum type.

## Documentation

Use plain English, without idioms, Latin abbreviations, or jargon. Assume the
reader is lightly familiar with MapLibre, but not with its internals.

Docs site pages introduce concepts and show common tasks, not every feature or
detailed contracts. Avoid bloating these; not every feature needs a section and
example on the docs site. Avoid narrating implementation details.

Guide pages share their prose across languages, so put language-specific code in
snippets. To name an API symbol in prose, write its C name as
`[](api:mln_map_set_style_url)`. The site shows the name in the reader's
language and links to that language's reference.

An API reference exists for each language binding; the C reference is the
source, and the rest are generated from there. The API reference describes
observable functionality and contracts; it must not narrate implementation.

Inline comments in the code explain constraints that the code can't show, such
as from a dependency, platform, vendor, or protocol that we can't change. If the
surprising behavior is rooted in our own code's design, rethink the code
instead.

### API reference comments

The C header comments are the API reference for every binding. mln-rs's
guidelines say how to write them. The generator copies each comment into every
binding, with C names and parameters spelled as that binding's symbols. It turns
`Returns:` and `Completes with:` into the binding's errors, and leaves
`Lifetimes:` in C.
